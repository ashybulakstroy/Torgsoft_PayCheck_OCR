# Техническое задание: геометрическое восстановление чеков по фотографиям смартфонов

**Файл:** `receipt_geometry_spec.md`  
**Проект:** `Prj_15_Torgsoft_Check_1C` — чеки Торгсофт → OCR → трансформация → 1С  
**Версия:** 1.0  
**Дата:** 25.10.2026  
**Статус:** ТЗ для реализации и экспериментальной проверки  
**Связанный документ:** `ocr_spec.md` (раздел 4.2 «Геометрия» и пункт 12.3). Настоящее ТЗ **детализирует** геометрический этап, не заменяя остальное ТЗ, OCR-движок или бизнес-правила интеграции.

## 1. Постановка задачи

Сотрудники фотографируют бумажные чеки и предзаказы смартфонами с разной высоты, расстояния и угла. Прямоугольная таблица на фотографии выглядит как трапеция или произвольный четырёхугольник: противоположные стороны не параллельны, горизонтальные и вертикальные линии наклонены. Иногда прямые линии дополнительно искривлены оптикой смартфона, а бумага может быть скручена или смята.

**Цель:** автоматически получить из исходной фотографии максимально геометрически корректное изображение документа и/или товарной таблицы для OCR, чтобы прямые строки и столбцы стали горизонтальными и вертикальными, без обрезания полезной информации и ухудшения распознавания букв, количества, цен и сумм.

**Важно:** точную исходную геометрию нельзя гарантированно восстановить из любого одиночного фото: для устранения оптической дисторсии нужны известные/оценённые параметры объектива, а для изгиба бумаги — локальная модель формы. В спорных случаях требуется контролируемый fallback, а не произвольная «красивая» деформация.

## 2. Границы и приоритеты

Входит в задачу:

- обнаружение границ листа и/или товарной таблицы;
- исправление ориентации, перспективы, остаточного наклона;
- выявление оптического искажения и его исправление **при надёжных параметрах**;
- опциональное локальное выпрямление нелинейной геометрии;
- проверка результата, сравнение с оригиналом, ручная коррекция углов в веб-интерфейсе;
- возвращение выровненного изображения, координат преобразования, метрик, статуса и диагностической информации в OCR.

Не входит в это ТЗ:

- замена Tesseract/PaddleOCR или дообучение моделей OCR;
- распознавание реквизитов, определение товарных строк, сверка сумм и налогов — это последующие этапы;
- искусственное восстановление размытого текста без сохранённой исходной информации;
- обязательная индивидуальная калибровка каждого смартфона.

**Приоритет:** (1) не потерять данные, (2) повысить OCR-точность, (3) снизить задержку. Запрещено принимать геометрическое исправление исключительно по визуальному впечатлению.

## 3. Условия эксплуатации

- **ОС/стек:** Windows 10 x64, Python текущего проекта; OpenCV `cv2` — использовать при наличии или добавить в контролируемом изменении зависимостей; `numpy`, Pillow по необходимости.
- **Ресурсы OCR-ПК:** ориентир — 10 ядер CPU, 16 ГБ RAM; фактическую конфигурацию измерить, не подразумевать отдельную видеокарту.
- **Вход:** JPEG с телефона; предусмотреть PNG/WebP и EXIF Orientation. Типичные JPEG — до нескольких МБ, но декодированный размер определяется разрешением, а не весом файла. Тестовый образец `1000697084.jpg`: 864 × 1536 пикселей.
- **Языки последующего OCR:** русский, казахский, латиница, цифры, специальные обозначения `Ø3`, `150*1,6`, `2,5 кг`, символ валюты.
- **Формат:** не только фискальные чеки; часто это предзаказ Торгсофт с таблицей `№ / Тауардың атауы / Саны / Бағасы`, несколькими печатными строками в одной позиции и отдельной строкой НДС.
- **Сеть:** после установки зависимостей обычная работа офлайн. Локальные преобразования не должны отправлять изображения во внешние облака.

## 4. Принципиальные типы искажений и способы решения

| Тип | Признак | Основной метод |
|---|---|---|
| Поворот изображения/EXIF | Чек лежит боком/вверх ногами | Приведение EXIF + оценка ориентации 0/90/180/270° |
| Перспектива плоской поверхности | Трапеция; прямые линии остаются прямыми, но не параллельными | Homography: `getPerspectiveTransform` + `warpPerspective` |
| Дисторсия объектива | Прямые линии выгнуты дугой, особенно к краям кадра | `undistort` либо `initUndistortRectifyMap` + `remap` с валидными параметрами камеры |
| Изгиб/скручивание бумаги | Изгиб линий меняется от места к месту | Опциональный local/page dewarping (геометрия сетки / UVDoc), только с проверкой качества |
| Слабый остаточный наклон | Строки отклонены от горизонтали после коррекции | Deskew по линиям таблицы/текста |
| Смаз, пересвет, низкое разрешение | Нечитаемые символы и пропавшие штрихи | Диагностика качества и запрос другого кадра; геометрия не восстановит утраченные пиксели |

**Запрет:** `minAreaRect` даёт *повёрнутый прямоугольник*, но сам по себе не восстанавливает произвольную перспективу; использовать лишь как часть fallback для deskew/ROI. Один `warpPerspective` не исправляет бочкообразное искажение и физический изгиб бумаги.

## 5. Архитектура модуля

Сделать изолируемый модуль, например `App/ocr_geometry.py`, с версионированным контрактом, который можно вызвать **до любого OCR-движка** и отдельно протестировать:

```python
result = rectify_receipt(
    image_bytes: bytes,
    *,
    mode: str = "auto",              # auto | perspective | original | manual
    manual_corners: list | None = None,
    camera_profile_id: str | None = None,
    options: dict | None = None,
) -> RectificationResult
```

Состав `RectificationResult`:

- `image`: выровненный RGB/BGR-массив `numpy.ndarray` без временного JPEG-перекодирования;
- `original_size`, `output_size`, `original_sha256`;
- `status`: `rectified`, `original_fallback`, `manual_rectified`, `needs_review`, `failed`;
- `method`: `homography`, `undistort+homography`, `local_dewarp`, `deskew_only`, `none`;
- `source_corners`: четыре точки в координатах исходного изображения либо `null`;
- `homography_3x3`, `inverse_homography_3x3`: матрицы, если применялись; для локальной коррекции — карта преобразований вместо одной матрицы;
- `quality_metrics`, `warnings`, `timings_ms`, `debug_artifacts` (опционально);
- `regions`: сведения об областях `paper`, `table`, `header`, `total`, если обнаружены;
- `transform_chain`: описание последовательных действий, чтобы пересчитывать OCR bounding-boxes в оригинал (EXIF, undistort, homography, локальная сетка, crop).

Если интегрировать через HTTP, использовать существующие роуты приложения по итогам аудита. **Не создавать новый публичный API и не менять контракт OCR без необходимости.** Для тестирования допустим служебный эндпоинт `/api/ocr/rectify` с возвратом `job_id`, `preview_url` и метаданных после согласования существующей структуры.

## 6. Алгоритм обработки: обязательный быстрый путь (MVP)

### 6.1. Приём и базовая оценка

1. Валидировать MIME/формат и предельные разрешение/декодированный размер (защита от слишком больших или повреждённых файлов).
2. Сохранить исходные байты *без изменений* (в рамках существующей политики хранения); вычислить SHA-256.
3. Прочитать EXIF Orientation, повернуть по ориентации один раз, сохранить соответствие координат исходнику.
4. Декодировать JPEG **один раз** в RAM. На рабочей копии оценить размер, контраст, пересвет, смаз (`variance of Laplacian` только как индикатор, порог калибровать), положение документа и относительный размер символов.
5. Создать уменьшенную копию (длинная сторона ориентировочно 1200–1600 px, **параметр для тестов**) только для поиска геометрии. Финальную трансформацию выполнять над исходным разрешением с пересчётом точек.

### 6.2. Выбор геометрического якоря: таблица или бумага

1. Сначала попытаться найти **таблицу**, особенно если видны её прямые границы и разделители: границы таблицы могут быть надёжнее изогнутых краёв бумаги.
2. Параллельный кандидат — контур **листа**: `grayscale`, мягкий blur, CLAHE только если нужно, порог/`Canny`, морфология, `findContours`, `approxPolyDP`.
3. Для таблицы: выделение горизонтальных/вертикальных линий направленной морфологией + `HoughLinesP` или эквивалент; группировка сегментов по углу и расстоянию; точки пересечения линий.
4. У каждой гипотезы сохранить `corners`, площадь, видимость/поддержку углов, согласованность с линиями таблицы, риск обрезания.
5. Выбрать кандидат не по максимальной площади, а по **геометрическому качеству и сохранности полезных областей**.
6. Если выпрямляется лишь таблица, исходный кадр и отдельные ROI шапки/итога оставить доступными: не потерять номер заказа, дату и сумму за пределами таблицы.

### 6.3. Проверка четырёх углов

- Гарантировать порядок `top_left, top_right, bottom_right, bottom_left` после ориентации кадра.
- Проверять выпуклость, отсутствие самопересечений, ненулевую площадь, минимальные длины сторон и устойчивость к шуму.
- Учитывать, что сильная перспектива создаёт почти сходящиеся стороны; жёсткая проверка соотношения сторон не должна исключать реальные длинные узкие чеки.
- Отбрасывать случаи с углами далеко за кадром, экстремальными коэффициентами увеличения, потерей края товарной части.
- Для таблиц с прямыми линиями выбирать углы пересечением **продлённых устойчивых линий**, а не координатами случайных пикселей контура.
- Если разница между несколькими кандидатами мала или уверенность низкая — статус `needs_review`, не принудительное выпрямление.

### 6.4. Перспективная коррекция

1. По четырём исходным точкам сформировать прямоугольник назначения.
2. Размер назначения рассчитать по геометрии граней и оценке соотношения сторон, сохраняя разумную высоту букв; не растягивать сверх реальной информации и не выбирать произвольно формат A4.
3. Вычислить `M = cv2.getPerspectiveTransform(src_pts, dst_pts)`.
4. Выполнить `cv2.warpPerspective` **один раз** на оригинальном разрешении с качественной интерполяцией (обычно `INTER_LINEAR`, отдельно измерить `INTER_CUBIC`), с безопасными полями.
5. Сохранить `M` и `M_inv` для подсветки OCR-координат на фото.
6. Применить остаточный deskew только если оценка по прямым строкам надёжна; не делать повторное лишнее вращение/ресемплинг при отклонении в пределах допуска.

**Важно:** не выполнять многократный `resize → rotate → warp → resize` над рабочим изображением. Все жёсткие преобразования желательно объединить в один итоговый ресемплинг после оценки параметров на копии малого разрешения.

## 7. Оптическая дисторсия смартфона: отдельно от перспективы

Исправление радиальной и тангенциальной дисторсии не должно быть слепым обязательным этапом.

### 7.1. Если есть калибровка конкретного смартфона

- Хранить профиль камеры (`device/model + camera ID + focal length/режим съёмки + разрешение/кроп + camera_matrix + distortion_coeffs + версия профиля`).
- При необходимости получать параметры по сериям снимков калибровочного шаблона через `cv2.calibrateCamera` (реально 10+ разнообразных ракурсов; контролировать reprojection error).
- Применять `cv2.undistort` либо `initUndistortRectifyMap` + `remap` до перспективной коррекции.
- Кэшировать карту корректировки для повторяющихся профилей и размеров кадра.
- Помнить, что смена модуля камеры, зума, фокусного расстояния и crop может сделать профиль неприменимым.

### 7.2. Если камера неизвестна (типичный случай)

- **Не придумывать** коэффициенты `k1, k2, p1, p2, k3` и не считать, что EXIF всегда содержит матрицу камеры.
- Сначала оценить кривизну длинных печатных линий таблицы и её изменение по кадру (многоточечные сегменты, отклонение от прямой).
- Если прямые линии достаточно прямые — не запускать `undistort`: исправлять только перспективу.
- Допустить экспериментальный `plumb-line`/самокалибровочный метод по нескольким надёжным горизонтальным и вертикальным линиям **как отдельный кандидат**, с регуляризацией и проверкой, что итоговое изображение действительно стало прямее и не исказились символы.
- Если достоверных параметров нет, `lens_correction_skipped=true`; это нормальное и безопасное поведение.

## 8. Изогнутая бумага и нелинейное выпрямление (второй этап)

Сильные изгибы бумаги или нелинейная кривизна строк **не** исправляются одной гомографией. Если после MVP линии таблицы остаются искривлёнными:

1. Оценить остаточную кривизну строк/столбцов по сетке таблицы.
2. Сформировать дополнительный кандидат `local_dewarp`, например локальное warping по сетке линий или отдельную модель **PaddleOCR Document Image Unwarping (UVDoc)**.
3. Не заменять рабочий OpenCV-контур тяжёлой нейросетью без сравнения скорости, RAM и точности OCR на реальных чеках.
4. При деформации по сетке не допускать складок и инверсий ячеек (проверка Jacobian/монотонности), резких переходов и «пережатия» символов.
5. Сравнить OCR на трёх вариантах — оригинал, homography, local_dewarp — по товарным строкам и числовым полям. Выбирать результат по валидируемым признакам и OCR-метрикам, не только по ровности рамки.
6. Для нелинейного преобразования сохранять карту обратного отображения координат; `M_inv` от гомографии уже недостаточна.

Встроенный в PP-StructureV3 параметр `use_doc_unwarping=True` существует, но **по умолчанию выключен**; тестировать его как альтернативу, а не считать автоматическим исправлением любого чека. Не устанавливать PaddleOCR в основное окружение без отдельного решения.

## 9. Контроль качества и автоматический выбор результата

Формировать кандидаты: `original`, `deskew_only` (если уместно), `homography_paper`, `homography_table`, `lens+homography` (когда разрешено), `local_dewarp` (этап 2).

**Быстрые геометрические метрики (до OCR):**

- средняя/95-й процентиль абсолютного отклонения длинных горизонтальных линий от 0°, вертикальных — от 90°;
- кривизна линий после исправления в пикселях/относительно размера;
- сохранность границ и всех ячеек таблицы;
- доля потерянных/обрезанных полезных пикселей;
- разумность локального изменения масштаба, отсутствие складок;
- детектированный угол, уверенность в найденных углах, стабильность к малым изменениям порогов.

**Метрики после OCR (только если последующий OCR доступен):**

- сохранность количества строк и позиций;
- точное совпадение чисел `количество`, `цена`, `итог`; арифметическая согласованность — **отдельная проверка**, не доказательство правильности текста;
- CER/WER для кириллицы и названий товаров на размеченных примерах;
- ошибки символов `0/O`, `1/I`, `5/S`, `Ø/0`, `*`, `,`, `.`.

Правило: применять новый результат автоматически только при достаточной геометрической уверенности **и отсутствии признаков потери данных**. При неоднозначности сохранить оригинал и обозначить `needs_review`. Не исправлять суммы «на глаз» и не отправлять сомнительные поля в 1С без проверки пользователя.

## 10. Ручная коррекция в существующем веб-интерфейсе

Предусмотреть режим `Исправить границы` (без обязательного отдельного экрана):

- слева/сверху исходная фотография; справа/снизу предпросмотр результата;
- четыре перетаскиваемые точки углов и зум/панорамирование; на сенсорном экране удобные зоны касания;
- при желании переключатель `По краям чека / По рамке таблицы`;
- кнопки `Авто`, `Применить`, `Использовать оригинал`, `Отменить`;
- после переноса углов немедленно обновлять preview (уменьшенное разрешение) и считать результат в исходном разрешении по подтверждению;
- не пересчитывать координаты неправильно при responsive-масштабировании: точки интерфейса передавать в **нормализованных [0..1] координатах исходного фото** с учётом EXIF;
- если лист обрезан или углы отсутствуют, показать причину и дать выбрать область **таблицы**, а не заставлять отмечать несуществующие углы листа.

Ручная коррекция геометрии — **отдельное действие** от пользовательского выбора соответствий номенклатуры 1С.

## 11. Производительность и работа с памятью

- Максимально обрабатывать `numpy.ndarray` в RAM; промежуточные файлы создавать только для debug/тестов/совместимости.
- Поиск контуров/линий — на уменьшенной копии, финальный resampling — на исходном размере.
- Не создавать десятки полноразмерных копий RGB одновременно. Контролировать пик памяти.
- Не запускать несколько конкурирующих 10-поточных OpenCV/Paddle/Tesseract-операций без контроля: oversubscription способен замедлить систему.
- Для **одного** чека сначала оптимизировать критический путь; для **нескольких** чеков отдельно тестировать пул 1/2/4/6/8/10 работников с ограничением внутренних потоков и RAM.
- Хранить кэш предварительно вычисленных карт `undistort` по профилю камеры/размеру.
- Прогрев моделей не должен входить в время рабочего инференса; в отчёте дать холодный и прогретый запуск.
- Предварительные **целевые ориентиры**, подлежащие проверке на целевом ПК: классический OpenCV-путь для фото до ~4 MP — медиана ≤ 0,7 с, P95 ≤ 2 с **без OCR**; для больших кадров и нелинейной модели фиксировать отдельные показатели. Это цель разработки, **не измеренная производительность**.
- Публиковать фазовые замеры: decode, detect, distortion, warp, deskew, save/serialize, OCR, total; CPU %, RSS peak, число процессов/потоков.

## 12. Структура исходников и данных

Предлагаемое разбиение, адаптировать под существующий проект после аудита:

Параметры хранить в конфигурации (не магические числа в коде). Регистрация этапов и профили камеры должны быть воспроизводимыми. При изменении алгоритмов сохранять версию `algorithm_version`.

### Рекомендуемый JSON результата

```json
{
  "schema_version": "1.0",
  "status": "rectified",
  "method": "homography_table",
  "algorithm_version": "geometry-1.0",
  "source_size": [864, 1536],
  "output_size": [760, 520],

В рабочем JSON передавать реальные `homography`/`map` по защищённому внутреннему контракту; пересчитывать точки обратно в оригинал с учётом всех трансформаций.

## 13. Обязательные тесты

### 13.1. Реальный предоставленный образец

Фотография `1000697084.jpg`: печатный предзаказ с таблицей из трёх строк (две товарные и НДС), разметкой на казахском, кириллическими/латинскими названиями, рукописной пометкой, штрихкодом и итогом `51 504,00 ₸`. Проверить:

- определение границ **таблицы** (приоритет), не ошибаться из-за неровного верха бумаги;
- линии четырёх колонок после коррекции; вертикальные разделители не должны «заваливаться»;
- не обрезаются названия, `30`, `370`, `6`, `5550`, `7104`, `1`, итог;
- область заголовка/итога остаётся доступна OCR, если корректировали только таблицу;
- результаты OCR «до/после» по специальным символам и числам.

### 13.2. Синтетические кейсы

На исходных сканах с известными прямоугольными таблицами синтетически моделировать углы поворота ±5/±15/±30°, перспективные трапеции, сжатие одной стороны, радиальную дисторсию, изменение освещения, отдаление, JPEG-сжатие. Сравнивать восстановленные координаты и OCR с эталоном. Сохранить случайный seed и параметры искажений.

### 13.3. Полевой корпус

Собрать минимум **50** реальных фото разных телефонов/углов (включая 10 заведомо проблемных): плоский лист, сильная перспектива, плохой фон, частично обрезанный лист, изгиб/волна, широкий угол, разное освещение, чек с переносами строк. Для каждых 10 примеров — ручная разметка четырёх точек, линий таблицы и критических текстовых полей. Не использовать один кадр как доказательство стабильного качества.

### 13.4. Регрессия и стабильность

- Повторный запуск на выровненном документе не должен накапливать геометрические искажения; контролировать флаг уже обработанного изображения.
- Повторная обработка исходного файла детерминирована при равной версии моделей/параметров.
- Повреждённый JPEG/нет документа/нет углов/EXIF rotation/изображение очень большого размера — корректный статус, без падения сервиса.
- Тест на RAM/CPU под одновременной загрузкой нескольких фотографий; приложение должно оставаться отзывчивым.
- Сравнение с прошлой стабильной версией OCR (без изменения OCR) по одному и тому же набору данных.

## 14. Измеримые критерии приёмки

1. **Готовность:** из существующего OCR-конвейера можно вызвать модуль для одного изображения и получить выровненный вариант, статус и обратное преобразование координат.
2. **Безопасность:** 100% тестовых входов либо корректно обрабатываются, либо возвращают управляемый `fallback`/`needs_review`; не бывает незаметного обрезания критических полей в варианте, автоматически выбранном для OCR.
3. **Геометрия:** на размеченных плоских чеках с четырьмя видимыми границами ≥95% фотографий в тестовом наборе проходят автоматическое выравнивание без ручного вмешательства; оставшийся угол линий после исправления (по размеченной сетке) ≤2° для 95% успешно обработанных примеров. Эти пороги — **целевые**, окончательно утверждаются по эталонному набору.
4. **OCR:** на одном и том же фиксированном движке не ухудшается точность критических чисел по сравнению с оригиналом на реальном тестовом наборе; для фото с заведомой перспективой демонстрируется измеримое улучшение CER/WER и/или точности числовых полей. **Не обещать 100% распознавания** только за счёт исправления геометрии.
5. **Ручной режим:** четыре точки можно скорректировать без перезагрузки изображения и сохранить точную обратную привязку к исходному кадру.
6. **Скорость:** предоставить P50/P95 (не среднее одного теста), худшие случаи и пик RAM для CPU/Windows ПК, сравнение оригинал/быстрый путь/тяжёлый путь.
7. **Сопровождение:** есть автотесты, конфигурация, краткая инструкция, примеры output, документ с результатами замеров.

## 15. Этапы реализации и ожидаемые артефакты

**Этап А — аудит существующего кода (без изменений рабочего OCR).** Найти текущую предобработку, путь поступления JPEG, преобразование EXIF, вызовы `cv2`, web-форму. Результат: файл `docs/receipt_geometry_baseline.md` с исходной точностью/задержкой и обозначением точек подключения.

**Этап Б — геометрия MVP.** Детектор таблицы/листа → 4 угла → perspective + deskew → проверка/безопасный fallback → метаданные. Результат: модуль, unit-тесты и сравнение на 50 фото.

**Этап В — интеграция.** Подключить **перед** OCR, настроить preview и ручные углы, координатную привязку, сохранение оригинала и диагностику. Результат: обработка чека через существующий пользовательский маршрут.

**Этап Г — оценка дополнительной коррекции.** Только после замеров: профили камеры/`undistort`, самокалибровка по линиям, UVDoc/local dewarp. Результат: решение включать ли каждый вариант по условиям и confidence, либо документированный отказ от него.

**Этап Д — оптимизация.** Эксперименты с кешем, уменьшенной копией, выбором интерполяции, CPU threads, процессами для пачки снимков. Результат: отчёт P50/P95, загрузка CPU, RAM, OCR accuracy before/after.

## 16. Правила реализации для Codex/разработчика

- Сначала открыть и соблюдать существующий `ocr_spec.md`; не ломать распознавание/трансформацию в 1С.
- Не заменять основной OCR-движок в этой задаче и не включать обучение моделей.
- Не подменять оригинал исправленным изображением: хранить их как разные сущности.
- Прежде чем изменять код, воспроизвести baseline и добавить замеры.
- Не пытаться автоматически «лечить» кривые линии произвольной гомографией.
- Отказ от автоматической коррекции — корректный результат при недостаточной уверенности.
- Исходный текст OCR, распознанные координаты и исправленные пользователем значения должны оставаться прослеживаемыми.
- Не копировать внешние репозитории без проверки лицензии, поддерживаемой версии и влияния на окружение.
